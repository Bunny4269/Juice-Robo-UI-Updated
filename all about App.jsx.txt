1. Imports
The imports bring the required React features, QR-scanning functionality, backend API functions, authentication utilities, and payment utilities into App.jsx.
React Hooks
	•	useState → Stores and updates application data/state.
	•	useEffect → Performs actions/side effects when the component loads or when specific data changes.
	•	useRef → Stores a value or reference without causing the component to re-render when that value changes.
	•	useMemo → Stores a calculated value and avoids recalculating it unnecessarily.
	•	useCallback → Stores a function so that the function is not unnecessarily recreated during every render.
QR Scanner
	•	jsQR → Reads camera/image pixel data and detects QR codes.
	•	It is used to scan the Juice Robo location QR code.
	•	The QR code identifies the outlet so the app can load the menu for that specific location.
Backend and Authentication
	•	api → Handles communication between the frontend and the backend APIs.
	•	onSessionExpired → Handles situations where the user’s login session has expired.
	•	isTokenValid → Checks whether the user’s authentication token is still valid.

3. Payment Engine Imports
These utilities control the UPI payment process.
	•	isMobileDevice → Checks whether the application is running on a mobile device.
	•	persistPaymentSession → Saves the current payment session so it can be recovered when the user returns from the UPI app.
	•	clearPaymentSession → Removes the saved payment session after the payment flow is completed or cancelled.
	•	formatUpiAmount → Formats the payment amount correctly for the UPI payment URL.
	•	validateBackendUpiUrl → Checks whether the UPI URL received from the backend is valid.
	•	buildBackendUpiPaymentUrl → Creates the final UPI payment URL used to launch the selected UPI application.

27. Payment Polling Refs and Controls
Payment polling checks the backend repeatedly to determine whether the payment has been completed.
The application limits polling to 5 attempts.
This prevents the application from continuously requesting the backend if the payment status cannot be confirmed.


⸻


28. Payment Verification Function
The payment verification function contacts the backend and checks the current payment status.
The application verifies the backend response before displaying the final payment status screen.
This prevents the frontend from incorrectly showing payment success simply because the user returned from the UPI application.


⸻


29. paymentCandidates
paymentCandidates is a list of possible field names and response locations where the backend may return payment status.
Different backend responses may use different names.
For example, the payment status may be returned as:
	•	payment_status
	•	paymentStatus
	•	payment_state
	•	paymentState
	•	status
	•	orderStatus
	•	order_status
It can also exist inside nested response objects.
The application checks these possible locations to reliably find the payment status.

38. Cancel Payment — handleCancelPayment()
Purpose: Allows the user to leave the current payment flow without falsely marking the order as paid.
The function handles cancellation of the pending UPI payment process.
Its responsibilities include:
- Stopping active payment polling.
- Clearing or resetting relevant payment UI state.
- Returning the user to the appropriate screen.
- Managing the persisted payment session according to the cancellation logic.
Important distinction: Cancelling the frontend payment flow does not necessarily cancel a transaction already initiated in a UPI application. Payment status must still be verified with the backend when necessary.

⸻

39.Polling Lifecycle and Cleanup
This section uses useEffect() to control when payment polling is allowed to run.
The cleanup logic calls stopPolling() when:
- The user leaves the upi-payment screen.
- The payment session is no longer available.
- The effect is cleaned up before it runs again.
Why this matters: It prevents a previous payment-verification process from continuing unnecessarily after the user changes screens.

⸻

40.Detect Returning From the UPI App
The browser-return handler detects when the user returns to Juice Robo after opening a UPI application.
It listens for three browser events:
- pageshow
- focus
- visibilitychange
Before starting polling, it checks that:
1. The current screen is upi-payment.
2. A payment session exists.
3. A UPI app was launched.
4. The browser was previously backgrounded.
5. The five-attempt polling limit has not been reached.
6. Another polling process is not already active.

If these conditions are satisfied, it calls startPolling(false).
This prevents the three browser events from accidentally starting duplicate payment-verification loops.Detect Returning From the UPI App

41. Detect Outlet Changes
The prevOutletRef reference stores the previously selected outlet.
When the outlet changes, the application:
1. Updates the stored previous outlet.
2. Clears the existing product list.
3. Resets the selected product and variant.
4. Loads the cart associated with the new outlet.
5. Updates the cart state.
Purpose: Prevents products and cart information from one outlet from being carried over incorrectly to another outlet.

56.Create or Resume Payment — handlePayment()
This function either resumes an existing payment session or creates a new order.
- Resume payment: Resets the polling state and opens the payment screen without creating another order.
- Create new order: Validates the cart, calls api.createOrder(), retrieves the order IDs, builds and validates the UPI URL, and saves the payment session.
- Error handling: Displays an error and resets the payment status if order creation or UPI validationpayment fails.

Important: Creating an order does not mean the payment is successful so, must be verified separately.

⸻

57. Prepare the UPI Payment Flow — handleProceedWithUpi()
This function makes the existing payment session ready for UPI payment.

this function does not itself launch the UPI app or open the app chooser. It prepares the payment state; the actual app-selection handler is handleSelectUpiApp.
